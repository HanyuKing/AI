# 第 5 章：评测、可观测性与安全

本章建立模型应用的回归闭环。每次修改提示词、模型、planner、工具 schema 或检索器，都要知道哪些问题变好了、哪些退化了；线上发生失败时，要能从脱敏 trace 还原请求走过的步骤。

## 学习目标

- 构造覆盖正常、缺参、模糊、越权、工具失败和对抗输入的评测集。
- 分开评估意图、工具选择、参数提取、检索来源与答案忠实度。
- 解释准确率的局限，理解 Recall@k、P50/P95、人工抽检和回归门禁。
- 设计结构化 Trace 字段，利用 request/trace ID 关联步骤并避免记录秘密。
- 理解 Prompt Injection 防护不能依赖关键词检测或提示词中的一句“忽略恶意指令”。
- 以最小权限、服务端校验、数据隔离、长度限制、审计和人工审批形成纵深防护。

## 概念讲解

离线评测集是一组固定输入、期望工具/参数/引用或人工参考答案。把模型输出和期望逐项对齐，才知道失败属于哪一层。本章 `cases.json` 覆盖六类请求；`evaluate.py` 分别计算 intent accuracy、tool accuracy 和 order ID 参数准确率。它使用规则预测器，不是 LLM Judge，也不衡量答案的语言质量或事实忠实度。

生产评测应额外包含：政策问题的标准来源、工具返回错误、模型拒答、用户改口、超长输入、跨租户、恶意检索文本、供应商限流和恢复路径。指标必须可操作：一个意图错分与一次越权访问的严重性不同，不能只汇总成一个平均分。

Trace 是一次请求的结构化事件序列，建议记录 trace ID、模型/提示词版本、检索文档 ID、工具名、状态、耗时、错误类别和 token usage。日志与 Trace 必须做访问控制和保留期限。标签不要放 user ID、完整问题或高基数值；PII 和凭据需要脱敏，原文通常不应被默认保存。本章只识别常见邮箱、手机号、Bearer token 与演示格式 API key；它不是通用 DLP，生产系统要按业务字段做结构化脱敏并验证绕过格式。

延迟看分位数而不是只看平均值：P95 表示 95% 的请求不超过该值，能暴露长尾。成本要把输入/输出 token 分开，按当期供应商价格计算估值；真实账单还可能有缓存、批量、区域和价格变化。本章的纯函数用于展示计算口径，不应把费率硬编码成永不过期的事实。

Prompt Injection 检测器只标记明显模式，攻击可以换语言、编码或上下文。本章 `inspect_untrusted_text` 不是过滤器，也不能把工具返回内容升级为指令。更可靠的原则是把用户/检索/工具文本隔离为数据，工具最小授权，所有写操作经过独立业务规则与审批。

## 代码阅读顺序

1. `cases.json`：看输入与每项期望值，而非只保存一个总答案。
2. `evaluate.py`：看每条用例如何产生可定位的失败项。
3. `trace.py`：看 metadata 与允许写入的字段、PII/凭据脱敏。
4. `metrics.py`：看 percentile 插值、延迟汇总与 token 成本估算。
5. `safety.py`：看输入长度拒绝、恶意文本标记，以及注释中声明的局限。

回归输出应保留逐条结果：

```python
{"intent_ok": True, "tool_ok": False, "order_id_ok": True}
```

这条用例告诉我们理解了用户意图、订单号也提取正确，但选择了错误工具。分项指标能指导修复，比“总准确率 83%”更有用。

## 动手运行

```bash
cd agent/learning_lab
PYTHONPATH=.:05-quality-safety python -m stage05.evaluate
python -m unittest discover -s tests -v
```

观察各项 accuracy 与未通过用例。再手工编辑一条规则，让“退款到哪一步”误判成物流，确认测试会指出 intent/tool 回归。Trace 示例可在 Python shell 中创建：

```python
from stage05.trace import Trace

trace = Trace(request_id="req-123", model="demo-model", prompt_version="support-v2")
trace.add("tool_call", "ok", tool="get_order", detail="customer a@example.com")
print(trace.export())
```

导出结果应含 `[EMAIL]`，不应有原始地址或认证凭据。

## 课堂实验

1. 每种工具错误至少增加一条评测用例，区分工具选择错误、参数错误、权限拒绝和工具超时。
2. 给政策问题增加 `expected_source_ids`，实现引用准确率；查询答对但引用错文件也应失败。
3. 收集一组模拟延迟，计算 P50/P95；讨论为什么均值无法反映长尾。
4. 注入手机号、邮箱、Bearer token 和 API key 到 Trace detail，确认日志只保留脱敏结果。
5. 把恶意提示放进政策文档内容，确认系统把它当作数据、拒绝将它作为工具调用权限来源。

## 课后作业与验收

- 建立至少 30 条脱敏用例，按意图/风险类别分层；保留每条失败差异。
- 设置回归门槛：总体指标下限、越权访问必须为 0、无来源政策回答必须拒答。
- 引入人工抽检或双人标注，记录参考答案争议；LLM Judge 只做辅助并抽样复核。
- 在 Trace 中记录工具耗时/错误码、检索文档 ID、提示词版本、token 数，不保存完整隐私正文。
- 设计灰度、A/B、回滚和反馈数据脱敏流程。

验收标准：变更可重复评测；失败能定位到调用步骤；日志没有 API key/PII；权限和审批由服务端执行；评测报告同时说明效果、成本和限制。
