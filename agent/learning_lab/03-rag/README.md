# 第 3 章：RAG 与业务知识

本章把可变的售后政策从提示词中移到可版本化知识库。RAG 的关键不是“把文档塞给模型”，而是可靠的数据摄取、授权过滤、召回、证据组织、引用和评估。当前代码实现透明的本地词法检索，便于看清步骤；向量检索是后续替换练习，不是当前实现的能力。

## 学习目标

- 说明文档来源、清洗、切块、元数据和更新/删除的生命周期。
- 解释关键词、BM25、Embedding、混合检索和 reranker 分别解决什么问题。
- 能在检索前执行 tenant/ACL/生效期过滤，避免召回越权内容。
- 让回答携带来源 ID 与版本；无命中时拒答或转人工。
- 区分知识库政策和订单/物流实时状态。
- 计算小型 Recall@k 并阅读失败样例，而非只看演示答案。

## 概念讲解

典型 RAG 流程为：文档摄取 → 解析/去噪 → 按语义与长度切块 → 保存来源/版本/权限元数据 → 用户问题改写（可选）→ 过滤 → 候选召回 → 可选重排 → 组装有限上下文 → 生成带引用答案 → 验证引用。切得过大容易带入无关内容，切得过小会失去条件与例外的上下文；应使用业务问题集实验，而不是凭直觉选 chunk size。

关键词检索对商品型号、政策条款编号和专有名词很有效；Embedding 对同义表达更友好；混合检索结合两者，reranker 再精排少量候选。本章使用中文二元词和 BM25 风格分数，是解释召回排序的教学替身，不具备成熟 tokenizer、向量语义或大规模索引特性。

权限必须在候选集合形成前过滤。若先取 top-k 再丢弃越权文档，可能造成结果缺失；若把未授权文本先送进模型再要求模型“不要引用”，内容已经泄露。政策版本和生效期同样要在检索层生效。召回结果带来源后，回答只允许基于这些证据；没有证据就承认查不到。

实时订单状态必须调用业务工具。RAG 回答“七日内可以申请”的政策并不能证明某笔订单已经签收七日或符合退款资格。

## 代码阅读顺序

1. `documents.json` 看来源、tenant、版本和生效时间元数据。
2. `ingest.py` 看按段落切块和逻辑文档替换；生产增量同步还需删除 tombstone 与失败重试。
3. `retriever.py` 看 `tokenize`、ACL 过滤、BM25 风格排序和 citation。
4. `answer.py` 看无证据时的拒答，以及回答中附来源和限制说明。

分数只用于排序，不是置信概率：

```python
candidates = [doc for doc in self.documents
              if doc["tenant"] == tenant
              and doc["effective"] <= today]
```

先形成允许访问的集合，再计算词频/IDF。`citation` 返回的是可追踪来源键，便于 UI 展示和回归评测。

## 课堂实验

1. 将长政策拆成 80、180、400 字块，比较同一测试查询的命中来源和上下文完整性。
2. 在 `cases.json` 为每个问题标注相关文档 ID，运行评测脚本，找出“召回不到”和“召回错文档”的区别。
3. 给一个政策增加新版本和未来生效时间；当前日期与未来日期分别查询，检查新旧版本。
4. 故意把 tenant filter 移到打分之后，编写用例证明会产生风险或结果质量退化，再恢复正确顺序。
5. 对没有命中、命中多个冲突版本、引用缺失的情况设计产品答复。

## 课后作业与验收

- 写一个 Markdown 导入器，保留标题路径、来源 URI、更新时间和 tenant。
- 用 SQLite FTS5/BM25、pgvector 或现有搜索引擎替换教学检索器；通过同一接口运行基准集。
- 增加 query、expected source、top-k result、citation correctness 与 Recall@k 报告。
- 做文档更新/删除回归，保证旧内容不再检索；增加租户、店铺、角色至少两层 ACL。

验收标准：每个政策答案都可追溯来源和版本；未命中不编造；ACL 在模型看到文本前执行；订单事实不从政策文档推断；检索质量有数据而非主观评价。
