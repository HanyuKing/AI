# AI Agent 工程师学习路线（电商后端方向）

> 面向有电商后端开发经验、希望转向 AI Agent 工程的工程师。路线以 6 个月、每周 8–12 小时为参考；已有 Python、云服务或搜索系统经验时可以压缩前置阶段。

## 目标岗位与能力画像

AI Agent 工程师不是“会写提示词的人”，也通常不需要从训练大模型开始。岗位核心是把模型接入真实业务，让它在可控权限下理解任务、选择工具、访问数据、按流程执行，并且能够评估、观测和持续改进。

常见岗位名称包括：AI Agent 工程师、LLM 应用工程师、大模型应用开发工程师、智能客服/AI 产品研发、AI 平台研发工程师。招聘要求大致可归纳为以下层次：

| 能力层 | 常见要求 | 后端经验的迁移方式 |
|---|---|---|
| 服务开发 | Python/Java/Go，REST/gRPC，异步并发，数据库、缓存、消息队列，Linux、Docker、云部署 | 直接复用 API、微服务、任务调度、容量与稳定性经验 |
| LLM 应用 | 主流模型 API，提示词，结构化输出，流式响应，函数/工具调用，模型路由 | 把模型当成有不确定性的外部依赖，做好超时、重试、降级和成本控制 |
| 知识与检索 | Embedding、向量检索、RAG、混合搜索、重排、文档解析与权限过滤 | 复用搜索、索引、数据清洗和业务权限设计经验 |
| Agent 与工作流 | 状态管理、工具编排、工作流/状态图、人工审批、恢复与幂等；熟悉 LangGraph 等框架 | 复用状态机、Saga、任务编排和领域流程设计经验 |
| 质量与运维 | 离线评测、线上反馈、Tracing、日志、指标、A/B、回归测试、可观测性 | 复用 SLO、链路追踪、告警、灰度和故障复盘经验 |
| 安全与治理 | 数据脱敏、租户隔离、Prompt Injection 防护、工具权限、审计、敏感操作审批 | 复用鉴权、RBAC、风控、审计和支付/退款保护经验 |
| 加分项 | MCP、语音/多模态、模型微调、私有化推理、K8s、GPU 推理优化 | 根据目标岗位补充，不要在基础应用能力之前分散投入 |

## 学习原则

1. **先有可运行的服务，再加 Agent。** 先学会可靠调用模型，再处理工具选择、检索和流程。
2. **先单 Agent 和确定性流程，再多 Agent。** 多 Agent 会增加调用成本、状态复杂度和调试难度，不是入门门槛。
3. **规则与权限放在代码和领域服务里。** 模型负责理解、选择和表达，不能成为退款、改价、发券等业务规则的最终裁决者。
4. **每个阶段都留下可展示的产物。** 项目、评测集、架构图和决策记录比课程清单更能证明工程能力。
5. **围绕目标职位学习。** 不必同时追逐所有模型、框架和向量数据库；掌握原理并能迁移比背 API 更重要。

## 6 个月路线

### 第 0 阶段：盘点与环境（第 1 周）

**目标：** 确认转型目标和现有能力缺口，搭好可重复的开发环境。

- 搜索目标城市/远程岗位，完成上面的 20–30 个职位采样，区分应用工程、平台工程和算法岗位。
- 盘点现有技术栈：语言、服务治理、数据库、消息队列、搜索、云平台、测试、监控。
- 确定一门主力开发语言。若 Python 不熟，使用 Python 做 AI 应用原型和工具服务；已有 Java/Go 生产系统经验继续保留，后续可用服务 API 集成。
- 配好 Git、虚拟环境/包管理、pytest、Docker、环境变量和密钥管理；将模型凭据放在环境变量或密钥服务中。

**产出：** 岗位需求矩阵、个人技能差距清单、一个可启动的 Python API 项目。

### 第 1 阶段：LLM API 与可靠服务（第 2–4 周）

**学习内容：**

- Python 工程基础（若已熟练可快进）：类型标注、Pydantic、async/await、异常处理、日志、pytest、依赖管理。
- 模型 API：消息格式、system 指令、temperature、上下文窗口、token、流式输出、结构化输出/JSON Schema。
- 可靠性：超时、有限重试与退避、速率限制、并发控制、熔断/降级、模型供应商适配、密钥与敏感字段脱敏。
- 生成的随机性：同一输入可能不同输出；对关键字段做 schema 校验、业务校验和可重试处理。

**实战：** 做一个“商品信息整理 API”：输入商品标题和规格，输出符合 schema 的标准化标题、属性和缺失字段提示。记录模型版本、耗时、token 用量和校验失败率。

**验收：** 有 API、流式和非流式接口、超时测试、格式异常处理、Docker 启动方式和最小回归集。

### 第 2 阶段：工具调用与确定性工作流（第 5–7 周）

**学习内容：**

- Function/Tool Calling 的调用循环：模型提出工具调用、服务端校验参数、执行工具、将结果回传模型。
- 工具契约：单一职责、参数 schema、明确错误类型、幂等键、权限上下文、超时和审计字段。
- Agent 与工作流的边界：适合模型选择的步骤用 Agent；分支明确、要求强确定性的步骤写普通代码或状态机。
- 多轮对话状态：保存必要状态，不把完整历史无限堆进上下文；处理用户改口、缺失信息、重复请求和取消任务。

**电商实战：售后查询助手 v1**

只读工具建议：

```text
get_order(order_id, user_id)
get_logistics(order_id)
get_after_sale_status(order_id)
search_after_sale_policy(issue_type, order_state)
```

先实现一个用户可用的流程：识别物流/退款/退货问题，询问必要信息，校验订单归属，调用正确查询工具，给出带数据依据的解释。第一版不执行退款、补发或改地址。

**验收：** 对工具调用做单元测试；未授权订单无法查询；模型不能自行编造订单状态；工具失败时有明确的用户答复。

### 第 3 阶段：RAG 与业务知识（第 8–10 周）

**学习内容：**

- 数据接入：HTML/PDF/Office 解析、去噪、切块、元数据、版本更新、删除和增量同步。
- 检索基础：Embedding、向量索引、BM25/关键词检索、混合检索、过滤、top-k、重排。
- RAG 质量：查询改写、上下文组装、引用来源、拒答条件、检索召回和答案忠实度。
- 多租户安全：检索前强制执行租户、店铺、角色和文档 ACL 过滤，不能依赖模型“记住不要看”。

**电商实战：** 把售后政策、物流规则、商品说明导入知识库。对容易改变的政策保存版本和生效时间；答案展示规则片段及来源。订单状态仍从订单/物流工具实时获取，不能用 RAG 文档替代实时业务数据。

**验收：** 建立一组问题及标准来源，测量 Recall@k/命中率、引用准确性和无依据回答率；更新或删除文档后旧内容不再被检索。

### 第 4 阶段：Agent 框架、状态管理与人工审批（第 11–14 周）

**学习内容：**

- 选择一个框架深入：优先理解 LangGraph 的状态、节点、边、条件路由、checkpoint 和 human-in-the-loop；同时用原生模型 API 写一个小型工具循环，理解框架解决了什么问题。
- 持久化状态、长任务、超时恢复、重复投递、幂等、取消和人工接管。
- 人工确认：在执行退款、补发、改价、改地址、发券等有业务影响的动作前展示对象、金额、原因和预期结果，审批后重新校验状态再执行。
- 结构化输出、确定性校验和状态转移；不把自由文本当成业务命令。

**电商实战：售后处理助手 v2**

在 v1 上加“生成处理草稿 → 客服审核 → 业务服务执行”的闭环。工具权限按只读/可写分级；执行工具只接受已审批的草稿 ID、当前操作者和幂等键，服务端重新检查订单状态与政策。

**验收：** Agent 重启可恢复；重复提交不会重复退款/补发；审批前不能调用写工具；审批后若订单状态变化则拒绝执行并要求重新处理。

### MCP 专项：标准化工具与资源接入（穿插第 5–14 周）

MCP（Model Context Protocol）是 Agent 连接工具、资源和提示模板的一种标准协议。它适合解决“同一组订单、商品、物流能力要被多个 Agent/客户端复用”的接入问题，但它不替代 Agent 编排框架、业务规则服务或鉴权系统。

**需要掌握的概念：**

- Host、MCP Client、MCP Server 的职责和通信边界。
- Tools、Resources、Prompts 的区别；工具输入输出 schema、错误返回和版本兼容。
- 本地进程与远程 MCP Server 的连接方式、会话生命周期、超时和断连恢复。
- 服务端鉴权、租户隔离、最小权限、审计、速率限制和工具调用确认。
- 不把 MCP Server 返回的文本当作可信指令；对返回结果做 schema 校验和内容隔离，防止 Prompt Injection 进入后续决策。

**电商实战：电商能力 MCP Server**

将售后 Agent 的只读能力封装成 MCP Server，至少提供：

```text
get_order
get_logistics
get_after_sale_status
search_after_sale_policy
```

再用一个 MCP Client 接入 Agent，验证同一套能力可以被客服 Agent 和运营分析 Agent 复用。退款、补发、改地址等写操作先不通过开放式 MCP 工具直接执行；如果确实需要暴露，必须使用独立权限、审批令牌、幂等键和服务端二次校验。

**学习顺序：**

1. 先用普通函数完成工具调用，理解参数校验、权限和错误处理。
2. 将只读函数改造成 MCP Server，使用 MCP Inspector 或等价客户端验证 schema、错误和连接生命周期。
3. 接入 Agent，比较原生工具调用与 MCP 接入的差异，记录延迟、失败和调试成本。
4. 增加鉴权、租户过滤、审计和人工确认，形成可展示的安全边界。

**验收：** 能画出 Host/Client/Server 架构图；能独立实现并测试一个 MCP Server；能解释 MCP 与 LangGraph、Function Calling、REST API 的关系；未授权用户无法通过 MCP 读取其他用户订单，写操作未经审批不会执行。

### 电商服务开放需要哪些协议

需要协议，但不是“所有服务都改成 MCP”。应按调用方和交互方式选择协议，常见的电商 Agent 协议栈如下：

| 问题 | 推荐协议/规范 | 作用 |
|---|---|---|
| 客户端如何调用业务接口 | REST/HTTP + JSON；内部高性能服务可用 gRPC/Protobuf | 订单、商品、库存、物流、售后等稳定业务 API |
| 客户端如何发现接口和参数 | OpenAPI 规范 + JSON Schema | 描述路径、方法、参数、返回值、错误码和鉴权要求；也方便生成 SDK 与工具定义 |
| Agent 如何统一发现和调用工具 | MCP | 将已有 REST/gRPC 能力适配为 Tools/Resources；适合多个 Agent 或客户端复用 |
| 用户/服务如何证明身份 | OAuth 2.0 + OIDC；服务间可结合 mTLS 或短期服务凭证 | 登录身份、租户、角色和授权范围；不能把 API Key 写进提示词 |
| 长任务和状态变化如何通知 | Webhook；事件较多时使用 AsyncAPI + 消息队列 | 物流状态变更、售后审核结果、库存变化等异步事件 |
| 写请求如何防止重复执行 | 幂等键、版本号/条件请求、明确错误码 | 退款、补发、扣库存、发券等重试安全和并发控制 |

推荐的分层方式是：

```text
电商领域服务
  -> REST/OpenAPI 或 gRPC/Protobuf（稳定业务契约）
  -> API Gateway（鉴权、限流、审计、版本、观测）
  -> MCP Server（面向 Agent 的工具/资源适配层）
  -> Agent Host/Client
```

例如，订单服务可以先提供 `GET /v1/orders/{order_id}` 的 OpenAPI 接口，再由 MCP Server 暴露 `get_order` 工具。MCP Server 负责把 Agent 的调用映射到业务 API，但订单归属、租户权限、退款资格和金额校验仍必须在领域服务或网关执行。这样既能让普通前端、客服系统和其他后端直接调用，也能让 Agent 使用统一的工具接口。

**开放 API 的最低要求：**

- 用 OpenAPI 写清请求、响应、分页、错误码、版本和废弃策略。
- 使用 OAuth 2.0/OIDC 或服务间凭证；每次请求从服务端上下文得到 `user_id`、租户和角色。
- 对退款、补发、改价、改地址等写操作要求幂等键、权限校验、审批状态和审计记录。
- 对 Webhook 验签、重放保护、重试退避和事件顺序做约定；不要让模型直接消费未验证的事件文本。
- 通过 API Gateway 做限流、配额、超时、日志脱敏和版本路由。

如果目标是让**另一个 Agent 直接调用你的能力**，可以优先做 MCP；如果目标是让前端、第三方系统和 Agent 都能接入，应先设计稳定的 REST/OpenAPI 或 gRPC 契约，再增加 MCP 适配层。只有在 Agent 之间需要委派任务、协商和回传结果时，才额外研究 A2A 等 Agent-to-Agent 协议。

### UCP：电商领域的互操作协议

UCP（Universal Commerce Protocol，通用商务协议）面向 **Agentic Commerce**：让 AI Agent、商家、平台和支付/履约系统用统一的电商能力进行互操作。它关注的是商品发现、购物车/结算、订单和售后等商业流程及能力表达；MCP 关注的是工具和资源如何被 Agent 发现、调用。两者不是替代关系，UCP 可以通过 REST、MCP 或其他协议绑定到具体实现，实际接入时应以当前版本的 UCP 官方规范为准。

可以这样区分：

| 规范 | 主要回答的问题 | 在电商 Agent 中的定位 |
|---|---|---|
| REST + OpenAPI | 业务接口长什么样、参数和响应是什么 | 你的订单、商品、库存、结算领域服务契约 |
| MCP | Agent 如何发现并调用工具/资源 | 把 `get_order`、`search_products` 等能力提供给 Agent |
| UCP | 不同商家/平台与 Agent 如何表达和完成标准化商业流程 | 商品发现、结算、订单管理、售后等跨平台电商互操作 |
| ACP（Agentic Commerce Protocol） | 购物 Agent 与商家如何协作完成电商交易 | 商品展示、Checkout、订单和支付相关流程；按目标生态选择适配 |
| A2A | Agent 之间如何委派任务和交换结果 | 例如导购 Agent 将履约问题转给售后 Agent |

**学习优先级：**

- 做企业内部客服或运营 Agent：先掌握 REST/OpenAPI、MCP、鉴权和业务规则，UCP 作为了解项。
- 做电商平台、商家 SaaS、购物 Agent、结算或跨平台商品接入：把 UCP 提升为重点，重点学习能力模型、发现机制、结算/订单生命周期、身份绑定和错误处理。
- 做通用 Agent 平台：同时理解 UCP 的电商能力层、MCP 的工具层和 A2A 的 Agent 协作层，避免把三者混成一个协议。

**作品集可以这样加一层：** 先用自己的订单/商品服务定义稳定的 OpenAPI，再提供 MCP 适配；最后为商品查询、购物车/结算、订单查询设计一个 UCP 适配层或兼容性示例。演示时明确哪些逻辑属于 UCP 的商业流程，哪些属于 MCP 的工具调用，哪些仍由领域服务负责。支付授权、库存扣减、退款金额和用户身份不能交给协议或模型直接决定。

### ACP：Agentic Commerce Protocol

在电商语境里，ACP 通常指 **Agentic Commerce Protocol**，用于让购物 Agent 与商家系统协作完成商品展示、结算、订单和支付相关流程。它和 UCP 都属于电商互操作层，具体能力、绑定方式和参与方会随版本与生态变化，学习或落地时必须以对应官方规范为准，不要把网上不同项目的 ACP 说明混在一起。

可以用下面的方式理解：

```text
用户/购物 Agent
  -> ACP 或 UCP（电商流程与能力互操作）
  -> 商家适配层
  -> 商品、库存、购物车、结算、订单、支付领域服务
```

**对电商后端工程师最重要的内容：**

- 商品发现和商品详情的标准化表达，以及价格、库存、促销和配送信息的一致性。
- Checkout/结算会话的创建、更新、确认、过期和状态机；购物车价格必须由服务端重算。
- 支付令牌化、支付授权、退款和风控边界；不要让模型接触原始卡号，也不要让模型决定支付金额或直接确认支付。
- 库存预留、订单幂等、并发状态变化、Webhook 验签、重放保护和审计。
- Agent 身份、用户身份绑定、商家授权和最小权限；协议适配层不能绕过现有订单与支付权限。

**学习与选型建议：**

- 内部客服/运营 Agent：ACP 先了解概念，优先完成 REST/OpenAPI、MCP、OAuth、订单状态机和评测。
- 做购物 Agent、商家 SaaS、支付/结算或平台级商品接入：把 ACP 与 UCP 放到重点，比较两者的商品、结算、订单、身份和支付流程，按目标合作方选择适配。
- 作品集不必同时实现完整 ACP 和 UCP；先实现一个规范化的商品与 Checkout 领域模型，再做一个 ACP 或 UCP 适配器，并展示幂等、库存、支付和订单状态测试。

**缩写歧义：** ACP 也可能指 Agent Communication Protocol（Agent 通信协议），它讨论的是 Agent 之间的消息交互，不是电商结算协议。看到招聘描述时要看上下文；如果岗位同时出现 UCP、checkout、payment、merchant，通常指 Agentic Commerce Protocol；如果出现 agent messaging、interoperability、A2A，则可能指通信协议方向。

### 第 5 阶段：评测、可观测性与安全（第 15–18 周）

**学习内容：**

- 离线数据集：真实问题脱敏后整理，覆盖常见问题、模糊表达、缺信息、对抗输入、工具错误和政策边界。
- 评测维度：意图分类、工具选择、参数准确、检索命中、答案正确/有依据、任务完成率、人工接管率、延迟和成本。
- LLM-as-a-judge 可辅助批量评估，但关键指标要有人工抽检和可复现的标准答案；评测模型本身也可能有偏差。
- Trace 每一步：会话/请求 ID、模型与提示词版本、检索文档 ID、工具名与耗时、校验结果、错误、token/成本。脱敏后设置访问控制和保留周期。
- 安全：Prompt Injection、越权工具调用、隐私泄露、拒绝服务、恶意超长输入、工具结果中的不可信文本、审计与速率限制。
- 线上策略：小流量灰度、回滚、人工反馈闭环、提示词/模型版本对照和回归门禁。

**验收：** 每次提示词、模型或检索变更均跑回归评测；可从 Trace 还原一次错误调用；敏感数据不会进入不必要的日志或外部模型请求。

### 第 6 阶段：上线化、作品集与求职（第 19–24 周）

**学习内容：**

- 服务部署：Docker、配置管理、CI/CD、健康检查、横向扩缩、队列化长任务、限流和成本预算。
- 生产设计：模型供应商不可用时的降级、缓存策略、数据隔离、SLO、容量估算和事故处理。
- MCP 进入必学的 Agent 工程基础：完成上面的只读电商能力 MCP Server 后，再根据职位要求补充远程部署、网关、OAuth 或企业级 MCP 平台。模型微调、开源模型推理与私有化部署仍按目标岗位选学。
- 求职材料：README、架构图、演示视频/GIF、评测报告、关键工程决策、故障案例和简历项目描述。

**验收：** 可在新环境按文档启动；有演示数据和端到端用例；评测报告能说明效果、成本、延迟和限制；不泄露生产密钥或真实用户数据。

## 作品集项目：电商售后 Agent

### 用户问题

“我的订单怎么还没到？如果今天收不到能退款吗？”

### 系统职责

- 识别问题类型并补齐订单号等必要参数。
- 验证当前用户对订单的访问权限。
- 从订单、物流服务读取实时状态；从带版本的知识库检索政策。
- 将可用方案交给确定性业务规则验证，再向用户解释依据。
- 对写操作只生成草稿，要求有权限的客服确认后由业务服务执行。

### 推荐架构

```text
客服/用户界面
  -> Agent API（鉴权、会话、限流）
  -> Workflow/Agent（状态、路由、提示词版本）
      -> 只读工具：订单、物流、售后状态、政策检索
      -> 规则服务：可选方案与资格校验
      -> 人工审批节点
      -> 写工具：按已审批草稿执行，并做幂等和审计
  -> Trace、指标、评测与反馈存储
```

### 核心工程要求

- `user_id`、店铺/租户和权限上下文由服务端注入，不能接受模型自行提供的身份。
- 工具必须做参数校验、鉴权、超时、审计和幂等；工具返回值要视为不可信输入。
- 退款资格由版本化规则服务判断；模型不得生成或修改退款金额。
- 写操作使用预览、明确确认和执行三段式；审批后执行前二次检查业务状态。
- 只向模型发送完成任务所需的最少数据；日志隐藏手机号、地址、令牌等敏感字段。
- 对每个回答标注数据来源或说明当前查不到；没有足够依据时询问、拒答或转人工。

### 作品集指标建议

先建立基线，再观察改动的影响，不必在没有数据时承诺具体效果：

- 正确订单识别率、工具选择准确率、工具参数通过率。
- 政策检索 Recall@k、引用正确率、无依据承诺率。
- 端到端任务完成率、人工接管率、重复联系率。
- P50/P95 延迟、每次会话 token/模型成本、工具失败率。
- 越权访问拦截率、未经审批的写操作次数（目标为 0）。

## 技术栈建议

| 方向 | 入门选择 | 说明 |
|---|---|---|
| 语言/API | Python + FastAPI + Pydantic | AI 应用库和资料丰富；生产服务可通过 API 与现有 Java/Go 系统协作 |
| 测试 | pytest、HTTPX | 对工具、权限、状态流转和失败分支做可重复测试 |
| Agent 编排 | 原生 API 起步，之后选 LangGraph | 先理解工具循环和状态，再学习框架抽象 |
| 工具互操作 | MCP Server/Client | 标准化暴露工具和资源；业务鉴权、规则和审计仍由服务端负责 |
| 持久化 | PostgreSQL；已有系统用现成关系库 | 会话、任务、审批、审计状态优先使用事务型存储 |
| 检索 | PostgreSQL + pgvector 或现有搜索引擎 | 小项目减少组件；更大规模结合向量与关键词检索 |
| 缓存/队列 | Redis、现有 MQ | 会话短状态、限流、异步任务按需求使用 |
| 观测 | OpenTelemetry + 日志/指标/Trace 平台 | 重点是端到端追踪和脱敏，不以某个厂商为学习目标 |
| 部署 | Docker、CI/CD、云容器平台 | K8s 根据目标岗位及团队规模选学 |

框架和模型迭代很快，选择依据应是岗位要求、社区维护情况、可观测能力、状态持久化和迁移成本。不要把“熟悉某个框架”当成 Agent 工程能力的替代品。

## 推荐学习资料

以官方文档和能运行的示例为主，学习时记录版本和完成日期：

- [OpenAI API 文档](https://platform.openai.com/docs/overview)：模型 API、工具调用、结构化输出与流式接口。
- [Anthropic 文档](https://docs.anthropic.com/)：工具使用、上下文和安全实践。
- [LangGraph 文档](https://docs.langchain.com/oss/python/langgraph/overview)：有状态 Agent 和人工介入工作流。
- [LangChain 文档](https://docs.langchain.com/)：检索、模型与工具集成；按需学习，不必全部掌握。
- [Model Context Protocol 文档](https://modelcontextprotocol.io/introduction)：理解 MCP 的 Host/Client/Server、Tools、Resources、Prompts 和安全边界。
- [Google UCP 文档](https://developers.google.com/merchant/ucp)：了解 Universal Commerce Protocol 的电商能力、互操作方式和当前规范；使用时以官方最新版本为准。
- [Hugging Face NLP Course](https://huggingface.co/learn/nlp-course)：补齐 Transformer、Tokenizer、Embedding 等基础概念；无需一开始通读全部模型训练内容。
- [FastAPI 文档](https://fastapi.tiangolo.com/) 与 [Pydantic 文档](https://docs.pydantic.dev/)：Python 服务和数据校验。
- [OpenTelemetry 文档](https://opentelemetry.io/docs/)：Trace、Metrics、Logs 的通用观测基础。

## 面试准备清单

- 解释一次完整的工具调用循环，指出哪些校验发生在模型外。
- 说明 RAG 的数据更新、切块、检索、重排、权限过滤和引用验证。
- 比较 Agent 和固定工作流：哪些节点交给模型，哪些节点必须确定执行。
- 设计一个退款/补发流程，讲清鉴权、权限、人工审批、幂等、并发状态变化和审计。
- 解释如何构建评测集，如何判断模型或提示词变更是否退化。
- 设计模型超时、限流、供应商故障、工具失败和长任务恢复方案。
- 讨论 Prompt Injection、检索文档中的恶意指令和敏感数据最小化。
- 展示真实项目数据：任务成功率、错误类别、延迟/成本，以及你如何迭代。

## 暂缓投入的内容

- 从零训练大模型、复杂数学推导：目标是 Agent 应用研发时，先学会模型 API、RAG 和线上工程。
- 一开始就搭多 Agent、复杂规划和大量工具：先用可解释的单 Agent 流程取得可靠基线。
- 同时学习多个编排框架或向量数据库：选一个做透，理解可迁移概念。
- 只做聊天 UI 或只展示“成功回答”的 Demo：没有权限、失败处理、评测和观测，难以体现工程能力。
